Independent IMU delivery (SDK1 / AVIA)

The SDK callback enqueues IMU packets and signals imu_semaphore_. A dedicated
worker drains that queue. The point-cloud worker no longer consumes IMU, so
publish_freq continues to control clouds without delaying IMU publication.

SignalOnce coalesces wake-ups under the semaphore mutex. IMU queue operations,
reset and diagnostic reads share a source-level mutex. A popped ImuPacket owns
its bytes, timestamp and device name; ROS publication runs outside that mutex.
The existing timestamp mapping, IMU values, frames and publisher QoS are kept.
The clock_status JSON adds imu_dropped_packets, cumulative per device handle
for the lifetime of the source. Queue capacity remains 256 packets.

Shutdown sets an atomic exit flag and wakes both workers. The node joins them
before stopping the SDK. SIGINT uses the application's rclcpp handler, rather
than installing a process-wide handler that calls exit() from a component.

Build with BUILD_TESTING=ON and run:
  colcon test --packages-select livox_ros2_driver \
    --ctest-args -R '^test_(imu_delivery|process_shutdown)$' --output-on-failure

Tests cover IMU-only input, payload/timestamp preservation, overflow, queue
wraparound under concurrent access, coalesced wake-ups, shutdown wake-ups and
component unload/reload with an explicit nonexistent device whitelist. The
separate process test sends SIGINT to the installed executable and verifies
exit status zero, including destruction of the SDK static logger. SDK1's
vendored spdlog symbols are hidden at link time to prevent ABI collisions with
the system spdlog used by ROS.

Measure on the driver host, with its ROS environment sourced:
  python3 scripts/measure_imu_delivery.py --seconds 60 --output /tmp/imu_run

The probe expects /livox/lidar to use CustomMsg (xfer_format=1). It records
monotonic callback time, system receive time and source timestamps separately.
Cloud callbacks receive serialized bytes; point deserialization happens only
after measurement. The IMU subscription is RELIABLE with depth 2048.

In a separate recording terminal/tmux pane, record /livox/imu and
/livox/clock_status to an MCAP bag, covering the entire measurement. Use
--qos-profile-overrides-path config/imu_record_qos.yaml so the independent
recorder can retain delayed samples. Then run:
  python3 scripts/compare_imu_bag.py --csv /tmp/imu_run/imu.csv \
    --bag /path/to/imu_bag --output /tmp/imu_comparison.json

Average topic rate alone does not establish timely delivery. Inspect callback
gap percentiles/maxima and measurement age as well. Nominal missing-slot counts
estimate source-time gaps; clock discontinuities must be investigated separately
and are not evidence of queue loss. A snapshot clock_status fault remains
latched by the existing clock mapper until the driver process is restarted.

Fast DDS publication mode

For rmw_fastrtps_cpp, launch the driver with:
  RMW_FASTRTPS_PUBLICATION_MODE=ASYNCHRONOUS ros2 launch ...

The C++ component leaves RMW configuration to its host. Configure the variable
before creating the ROS context, or set it in the launch Node's additional_env
for an executable. This retains RELIABLE QoS and source timestamps. Explicit
XML QoS overrides take precedence; check the actual process environment.

In a physical AVIA test, synchronous rcl_publish blocked for 331-333 ms when
new subscribers joined. IMU and cloud queues accumulated despite independent
workers. A 90-second asynchronous trial with eight subscriber join/leave cycles
had a maximum IMU callback gap of 14.74 ms and no missing source slots; all
18,271 samples matched the independent bag. Longer validation remains required
for the target workload. Details of the RMW setting:
https://github.com/ros2/rmw_fastrtps/blob/humble/README.md#change-publication-mode
